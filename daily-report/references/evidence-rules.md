# 证据与表达规则

## 个人归因

仅将以下内容作为个人工作证据：

- 配置邮箱匹配的 Git 提交。
- 当前用户执行或明确推进的待办。
- 当前用户参与的工作日程。
- 当前用户发送、回复、被 @、被明确分派或确认参与的白名单群消息。
- 个人复盘阶段中，与已确认日报有关的私聊和听记。

群内其他人讨论的模块、提交或计划不能单独成为用户工作项。可以用前后消息理解一个已归因事项，但不得把上下文改写成新的个人产出。

## 状态

- `已完成`：有明确完成、验收、测试通过、提交并确认合入等证据。Git 提交本身最多证明“代码已提交”。
- `推进中`：已经开始、正在联调、排查、评审或等待验证，但缺少完成证据。
- `待确认`：规则、依赖、结论或归属不足以确认。
- `阻塞`：缺少依赖、环境、接口或明确决策，导致无法继续推进。

不能把“讨论”“查看”“被提及”“有人提交”写成“完成”。聊天与 Git 冲突时降低结论强度并标记待确认。

## 不编造红线与稀疏兜底

具体数字、客户或单位名、时间节点、他人行动必须有来源（Git、DWS 或用户补录）；无来源时不写，宁可用“多个模块”“多轮沟通”这类模糊表达，也不要把推断写成事实。这条红线优先于任何模板完整性要求。

证据稀疏时不硬凑：不写“今日无工作”，不把单条证据拆成多条充数。先展示覆盖缺口并请用户补录；用户明确无补充时，允许输出只含已有证据的短草稿。

## 候选与手工补录

从消息、待办和提交推导出的后续事项只能放入“候选建议”。用户确认后才进入“明日计划”。

自动来源为空时，先展示覆盖范围，再允许用户补录动作、对象、结果或状态；手工补录与自动证据同样需要在草稿中清晰标识。

## 去重与业务线聚合

将同一业务事项的提交、沟通、日程和待办聚合为一项。判断“同一事项”的线索：同一分支或需求编号、提交信息与群消息中的共同关键词、同一模块或页面。不确定时宁可分开，不要把不相干的事硬合并。

周报与月度总结必须做跨天聚合：同一业务事项在多天日报中出现时，合并为一条业务主线，按“背景 → 本周期进展 → 现状或问题 → 下一步”叙述，而不是按天罗列动作。读者看完应知道这件事到哪了、往哪去，而不只是“做了什么”。

## 业务化改写

“今日工作（可复制）”按“动作 + 对象 + 结果或状态”写成 3–6 条，不保留来源标签、提交哈希或无关技术细节。低价值或纯技术措辞改写为业务友好表达，例如：

| 原始措辞 | 改写后 |
| --- | --- |
| 解决冲突 / merge dev | 代码集成与稳定性维护 |
| fix typo / 改错别字 | 细节修正（合并进所属事项，不单独成条） |
| 调样式 / 改 px | 页面样式优化 |
| 回滚提交 | 方案调整（说明调整后的方向） |

改写只能换措辞，不得提升事实强度：不能把“已提交”改写成“已上线”“已验收”。事实留档部分保留原始措辞。

## 读者视角过滤清单

同一条证据在不同产出中的取舍：

| 信息类型 | 事实留档（已完成/推进中） | 今日工作（可复制） | 个人复盘 |
| --- | --- | --- | --- |
| 提交哈希、分支名、PR/需求编号 | 保留（下钻凭证） | 移除 | 保留 |
| 技术实现路径细节 | 简要保留 | 移除，只留业务结果 | 保留（支撑反思） |
| 谁@谁、员工间分工对话 | 仅作归因依据，不成条 | 移除 | 提炼为协作观察 |
| 来源标签（Git/群/待办） | 保留 | 移除 | 保留 |
| 风险、阻塞、需决策事项 | 保留 | 保留（放末条或单列） | 保留并展开 |

周报、月度总结面向更高层读者，按“今日工作（可复制）”一栏的口径过滤，额外突出风险与需协作事项。

## 脱敏

正式日报、周报和复盘默认移除或概括：内部 IP、账号、手机号、邮箱、群 ID、完整链接、令牌、凭证、服务器地址和客户敏感信息。姓名优先替换为“产品”“测试”“前端同事”等职责。私聊只提炼与工作决策直接相关的结论。
